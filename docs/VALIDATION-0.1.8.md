# v0.1.8 검증 · 2026-09-10

## 변경

매번 모든 일정·할 일 본문을 순서대로 받던 네이버 동기화를 개선했다. 초기 조회는 독립된 캘린더·컴포넌트를 최대 3개까지 함께 요청한다. 이후에는 전체 조회 범위의 URI·ETag 목록을 확인하고, 같은 강한 ETag의 저장된 본문을 재사용한다. 새 항목·변경 항목만 GET 또는 최대 50개 단위의 calendar-multiget으로 가져온다. HTTP 연결도 공유한다. 의존성은 추가하지 않았다.

기간을 축소하거나 삭제 확인을 생략하지 않는다. 본문이나 강한 ETag가 없는 항목은 다시 읽는다. GET 본문의 버전은 GET 응답에서 취한다. metadata REPORT 미지원(400/405/501), multiget 미지원(400/403/405/501)은 기존 전체 조회로 복귀한다. 다른 인증·서버 오류, 누락·중복·다른 출처의 응답은 실패로 처리하고 기존 캐시를 유지한다. 정상적으로 빈 결과를 확인했을 때는 삭제를 반영한다. 할 일만 실패하면 기존 할 일을 유지하면서 정상 일정은 갱신한다.

이 방식은 [RFC 4791 §8.2.1.3의 URI·ETag 비교와 변경 리소스 조회](https://www.rfc-editor.org/rfc/rfc4791.html#section-8.2.1.3)에 따른다. 클라이언트 공유는 [사용 중인 OkHttp 4.12.0의 공식 소스 안내](https://github.com/square/okhttp/blob/parent-4.12.0/okhttp/src/main/kotlin/okhttp3/OkHttpClient.kt)를 확인했다.

최신 사용자 요청에 따라 기존 ‘수동 새로고침에서만 스피너 표시’ 규칙을 변경했다. 앱 새로고침과 네이버 백그라운드 조회 중에는 상단 스피너를 표시하고, 완료·실패·취소 후 제거한다. 다음 실행 때 다시 표시하며, 캐시와 기존 화면은 유지한다. 로그인 후 시작되는 초기 동기화 상태도 공유한다. 1분 타이머는 현재 동기화 상태를 확인해 중복 요청을 피한다.

Google은 [ContentResolver.isSyncActive](https://developer.android.com/reference/android/content/ContentResolver#isSyncActive(android.accounts.Account,%20java.lang.String))와 실행 상태 변경 알림으로 선택 계정의 활성 동기화를 확인한다. 필요한 [READ_SYNC_STATS는 normal 권한](https://developer.android.com/reference/android/Manifest.permission#READ_SYNC_STATS)이며 별도 사용자 허용 창은 없다. 예약·대기 상태만으로 스피너를 계속 표시하지 않는다.

## 성능 측정

MockWebServer에 캘린더 3개, 일정 180개, 할 일 60개를 구성했다. 각 응답에 100ms 지연과 32KiB/20ms 본문 전송 제한을 적용했다. 아래 수치는 같은 실행의 순차 전체 조회와 개선된 조회를 비교한 결과다. 캘린더 탐색(PROPFIND), 실제 TLS 연결, Android 화면 렌더링은 측정에서 제외했다.

| 방식 | 시간 | 응답 본문 바이트 | HTTP 요청 | 받은 iCalendar 본문 |
| --- | ---: | ---: | ---: | ---: |
| 순차 전체 조회 | 1,007ms | 509,034 | 6 | 240 |
| 병렬 초기 조회 | 322ms | 509,034 | 6 | 240 |
| 변경 없는 재조회 | 224ms | 40,242 | 6 | 0 |

동일한 이벤트·할 일 결과를 확인했다. 변경 없는 경우에도 목록 조회는 수행하므로 요청 수는 6회로 같고, 줄어든 것은 본문 전송량이다. 바이트 수는 응답 본문 기준으로 실제 모바일 네트워크의 전체 전송량과 다르다. 구현 전 기준 측정은 `baseline.json`, 같은 실행의 비교값은 `benchmark.json`에 있다. **실제 네이버 서버 속도를 측정하거나 이 개선 비율을 보장하는 결과는 아니다.**

API 35 전용 에뮬레이터에서 실제 앱·저장소·Keystore·Calendar Provider를 사용했다. 네이버 응답은 격리된 HTTPS fixture이며 실제 사용자 계정을 사용하지 않았다. Google 클라우드 전송과 실제 Google sync adapter 활성 상태는 검증하지 못했다. Galaxy 실기기, 실제 네이버 서버의 multiget 호환성과 실제 계정별 성능은 미검증이다. 미지원 REPORT는 전체 조회로 복귀할 수 있어 효과가 계정·서버에 따라 달라진다.
